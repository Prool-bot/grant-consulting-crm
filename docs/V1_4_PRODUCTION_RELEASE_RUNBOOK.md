# CRM 1.4 — фінальний контрольований перехід із робочої CRM 1.3

**Статус:** GO/NO-GO план; **production release НЕ санкціонований і НЕ виконаний**. Оновлення вихідного коду production Apps Script, зміна поточного WebApp deployment, Script Properties або запис у робочу Google Sheets потребують окремого прямого дозволу власника. PR #10 тримати Draft.

## 1. Підтверджені передумови (05.11.2026)

- Ізольована CRM 1.4: фактичні read-only preflight та integrity тестової Sheets, окремий синтетичний CRUD, **одна** погоджена подія через CRM → Google Calendar, підтвердження власником тестового WebApp `/dev`, синтетичні backup → restore. Автоматичні тести CI: **214/214**.
- Доступна робоча CRM 1.3, поточне активне розгортання WebApp: **версія 6** від **22.10.2026 12:57**. Власник зберіг чинний **deployment ID і URL** приватно. Не передавати ідентифікатори/токени до публічного репозиторію.
- **Незмінна робоча Google Sheets** визначена з `CRM_SPREADSHEET_ID` активного Apps Script. У Drive назва цієї робочої таблиці **`CRM_DB_TEST`**; попри назву `TEST` це саме значення властивості робочого Script. **Не переорієнтовувати** Script Property через назву файла.
- Незалежна приватна копія `CRM_1_3_BACKUP_2026-11-05_before_1_4`, створена власником, звірена з робочою базою. Окрема приватна `CRM_1_3_RESTORE_REHEARSAL_2026-11-05` створена **із backup**, а не з робочого оригіналу. На всіх базах усі 12 вкладок; для backup і rehearsal збіглися усі дев'ять entity-таблиць, control та journal. SHA-256 **обох підтверджених журналів** перевірені; `schema=2`, `modelVersion=12`, `pending=false`, зв'язки без осиротілих записів. Файли приватні; жодних клієнтських значень не публікувати.
- Реальне `SheetsRepository.restore()` було перевірено **на повністю синтетичній** базі; для реальних даних перевірено відтворення цілого файла Google Sheets із незалежної копії. Ці результати **не тотожні**.

## 2. Що залишається до дозволу на release

1. Власник окремо підтверджує **дозвіл саме на оновлення production**. Без нього **не запускати** workflow `.github/workflows/apps-script-production-stage.yml`; не робити release-prefixed commit, `clasp push`, merge, `Deploy` або зміну WebApp version.
2. У момент оновлення переконатися, що всі поточні CRM-записи завершено; тимчасово закрити активні вікна робочої CRM. Перевірити, що **свіжа резервна копія** ще відповідає поточному журналу. Якщо після 05.11.2026 були нові записи, створити нову приватну копію **перед** розгортанням.
3. У приватному сховищі ще раз звірити deployment ID, номер **6**, попередній URL `/exec` і базові Script Properties: `CRM_ENABLED`, `CRM_OWNER_EMAIL`, `CRM_SPREADSHEET_ID`. Не міняти `CRM_SPREADSHEET_ID`.
4. Перевірити OAuth-права production: нова CRM 1.4 додає `https://www.googleapis.com/auth/calendar` до чинних `spreadsheets` і `userinfo.email`. Перед введенням у дію власник має надати потрібний доступ у **своєму робочому** Apps Script. `CRM_CALENDAR_ID` не потрібний для основного власного календаря. Час **нових** дій `Europe/Istanbul`; чинні старі дії без time zone — `Europe/Kyiv`.
5. Переконатися, що PR #10 містить остаточно погоджений commit і зелений CI; випускати тільки всі **чотири** файли однієї збірки: `Code.gs`, `Server.gs`, `Index.html`, `appsscript.json`.

## 3. Послідовність дозволеного переходу (лише після окремого «Так, запускаємо CRM 1.4»)

1. **Freeze / backup.** Власник підтверджує коротке вікно без нових записів. Звірити контрольну ревізію та незалежну backup-копію; не змінювати production Sheets та Script Properties.
2. **Stage source.** Окремо погодженим release-комітом запускається `.github/workflows/apps-script-production-stage.yml`, який перевіряє PIN SHA-256 production Script ID і відмінність від staging та виконує `clasp push` **лише HEAD коду** production Apps Script. Цей крок **не оновлює** існуючий `/exec` WebApp.
3. **OAuth.** Власник у робочому Apps Script перевіряє новий `calendar` scope та погоджує запит Google. За помилки — зупинити подальший deployment. Не створювати реальних календарних подій для діагностики без нового дозволу.
4. **Versioned deploy.** У `Deploy → Manage deployments` вибрати **існуючий активний** WebApp deployment ID; **Edit → New version → Deploy**. Не використовувати `New deployment`, не змінювати доступ `MYSELF` / `USER_ACCESSING`; `/exec` URL повинен лишитися **тим самим**.
5. **Перший smoke, тільки читання.** Перевірити авторизацію власника, відкриття `/exec`, каталог, клієнта, вкладки, пошук, заявки; звірити контрольні кількості/реєстри. Виконати тільки read-only `crmCalendarCheck`, не запускати `crmCalendarSync`, поки власник не погодить окрему дію.
6. **Завершення.** Зафіксувати новий deployed version, фактичний URL без його публікації, статус CI і результат read-only smoke. Відновити роботу користувача тільки після успішних перевірок.

## 4. План rollback

- При проблемі **зупинити нові записи** та спочатку зафіксувати приватний стан бази після спроби випуску, включно з pending транзакціями.
- Повернути **той самий deployment ID** на **стару версію 6** у `Manage deployments → Edit`; не створювати новий `/exec` URL і не змінювати клієнтський Google Sheet ID.
- Відкат версії коду **не відкочує дані**: якщо після оновлення були нові клієнти/заявки/події, **не підміняти** робочу базу старою копією, інакше вони будуть втрачені. Відновлення даних — тільки після окремого рішення власника та аналізу фактичного журналу.
- Після rollback перевірити читання/авторизацію CRM 1.3 та сумісність її форм із поточними даними. Не «лікувати» помилки очищенням журналу чи `repairCrm_` без окремої контрольованої процедури.
- Production Apps Script HEAD після `clasp push` може містити код 1.4 навіть при поверненні versioned WebApp на версію 6. Це важливо для ручних запусків з редактора; в разі повного відкату HEAD робити це окремим контрольованим кроком із архівної копії.

## 5. GO / NO-GO

**GO** тільки за одночасного виконання: (а) прямий дозвіл на production release, (б) свежий production backup, (в) старий active deployment ID/URL/version 6 збережені приватно, (г) зелений CI, (ґ) погоджені OAuth scope і часовий пояс, (д) план швидкого повернення до версії 6.

**NO-GO** у разі будь-якої невизначеності ID, відмови OAuth, невідповідності контрольного журналу, нових непідтверджених записів або невдалої збірки. На цьому документі **GO ще не наданий**.

Власник не має передавати повні Script ID, Spreadsheet ID, deployment ID, URL приватного WebApp, e-mail, токени чи вміст клієнтських рядків у чат або публічний GitHub.
