# Остаточне оновлення CRM 1.2 → CRM 1.3

Інструкція для ручного випуску власником після окремого рішення. Цей PR не виконує merge, deployment або зміни робочих ресурсів. Код готовий до контрольованого випуску після успішних перевірок; завершення наведеного приймання підтверджує власник.

## Сумісність і дозволи

Для вже чинної CRM 1.2 з modelVersion=12 і schema=2 міграція не потрібна. Не запускати setupCrm_, migrateCrm12_, repairCrm_ чи restoreCrm_ як частину оновлення. Не змінювати заголовки, рядки, журнал або керівну комірку Sheets. Нові поля CRM 1.3 необов’язкові; частковий запис, UUID, квитанції requestId, контрольні суми, ревізії та recovery збережені.

OAuth без змін: spreadsheets — читання/запис чинної бази; userinfo.email — перевірка власника. Доступ MYSELF, виконання USER_ACCESSING. Gmail, Calendar, Drive API, ШІ та додаткові сервіси не потрібні.

Стандарт читання — bounded_range. За замірами власника 2063 → 1351 мс (−712 мс, −34,5%), без помилок. Діагностика неактивна без одночасних CRM_ENVIRONMENT=test і CRM_DIAGNOSTICS_ENABLED=true; у production немає діагностичних таймерів/звітів. Тестовий перемикач збережено, додаткові порівняння не потрібні.

## До зміни коду

1. Зафіксувати приватно чинний /exec URL, deployment ID, номер версії CRM 1.2 та копію її коду/маніфесту. Не додавати їх або значення Script Properties до GitHub чи публічних журналів.
2. Завершити всі збереження CRM 1.2; при невідомому результаті повторити початковий запит у тій самій вкладці. Не закривати вкладку з непідтвердженим запитом. Після підтвердження закрити всі вкладки CRM на час оновлення, щоб старий UI не записував паралельно.
3. Створити незалежну приватну копію всієї таблиці засобами Google Sheets, включно зі службовими аркушами та журналом. Переконатися, що копія відкривається й повна. Зберегти контрольні кількості клієнтів/заявок/контактів/документів/партнерів приватно. Не підмінювати CRM_SPREADSHEET_ID адресою копії.
4. Перевірити придатність резервування/відновлення в ізольованому середовищі; функціональні CRUD-тести виконувати на синтетичній базі. Провести ручний огляд docs/SECURITY.md і застосовних пунктів docs/ACCEPTANCE.md. Приймання каталогів CRM 1.3: docs/V1_3_CLIENT_CATALOG.md. Майбутні модулі Calendar/фінансів/ШІ не є частиною цього випуску.
5. Із погодженого коміту PR №9 виконати npm test, npm run build, node scripts/verify-cloud-release.js. Використовувати всі чотири файли однієї збірки dist/apps-script: Code.gs, Server.gs, Index.html, appsscript.json. Не змішувати UI/сервер різних версій, не переносити dist/local.

## Оновлення з тією самою адресою

1. Відкрити саме чинний Apps Script-проєкт CRM 1.2. Замінити в ньому чотири файли збірки; HTML-файл у редакторі має назву Index. Зберегти код. Не створювати нового проєкту або таблиці.
2. Зберегти CRM_OWNER_EMAIL, CRM_SPREADSHEET_ID та CRM_ENABLED без змін. У робочому проєкті CRM_ENVIRONMENT=production (або відсутній), CRM_DIAGNOSTICS_ENABLED=false (або відсутній); видалити CRM_PROJECTION_READ_MODE. bounded_range діє без додаткового налаштування. Не запускати benchmarkCrmRead_ у робочому проєкті.
3. Deploy → Manage deployments → вибрати чинне активне розгортання з записаним deployment ID → Edit → Version: New version → опис CRM 1.3 і погоджений коміт → Deploy. Перевірити MYSELF / USER_ACCESSING. Не використовувати New deployment; не архівувати чинне розгортання.
4. Звірити отриманий /exec URL з приватно збереженим: він повинен збігатися. Редагування версії наявного deployment зберігає URL та ID: [офіційна документація Google](https://developers.google.com/apps-script/concepts/deployments#edit_a_versioned_deployment).

## Приймання після оновлення

- Відкрити стару закладку /exec у новій вкладці, перевірити власника, каталог і досьє, кількості та зв’язки наявних записів. Архівні/м’яко видалені записи перевіряти з відповідними фільтрами, вони не повинні зникнути з бази.
- Перевірити відмову сторонньому акаунту та анонімному браузеру; не розширювати доступ у разі помилки. Перевірити телефон і комп’ютер, пошук/фільтри, нові поля каталогу. Не створювати демонстраційних записів у робочій базі.
- Першу необхідну робочу зміну виконувати лише після успішної перевірки читання; підтвердити результат повторним відкриттям. При невідомому результаті не створювати нового запиту — повторити початковий з тим самим requestId у відкритій вкладці.
- Підтвердити відсутність crm_repository_timing у робочих виконаннях. Дані й Google ID не копіювати до PR. Зберегти резервну копію та попередню версію коду.

## Якщо виникла проблема

При помилці цілісності зупинити записи. Не очищати журнал, не виправляти контрольні суми й не запускати repair/restore навмання. Зберегти приватну копію поточного стану, включно з можливими новими записами; діагностувати на ізольованій копії.

Відкат коду: у Manage deployments для того самого deployment вибрати збережену попередню версію CRM 1.2, зберігши URL і права. Перезавантажити всі вкладки. Перед подальшими записами перевірити сумісність на ізольованій копії, особливо якщо вже використані нові типи/поля CRM 1.3. Відкат коду не відкочує дані. Не замінювати робочу базу передрелізною копією: це втратить нові записи. Відновлення даних — окрема погоджена процедура після аналізу стану.
