# М2.5 — серверне сховище Google Sheets

## Обсяг і стан

Підготовлено локально в гілці `codex/m25-google-sheets` від `origin/main` після PR №3 (`51f2787`). Нових залежностей немає. Google-файли, Apps Script-проєкти, OAuth-авторизації та веброзгортання не створювались. Gmail, Calendar, Drive API та ШІ не підключені. М3 не розпочато.

`SheetsRepository` використовує бізнес-логіку М2 `CrmService` без зміни форм, статусів, валідації заявок, архівування та м’якого видалення. Локальний інтерфейс М2 й надалі зберігає **лише вигадані дані в браузері**. Серверний API та збірка готові до окремого тестового підключення; перемикання інтерфейсу на асинхронний API не виконано. `doGet` не видає локальний демонстраційний HTML за продуктивну CRM: без конфігурації він закритий, після ввімкнення показує повідомлення про готовність сервера. Публікація не входить до М2.5.

## Формат бази

Створюються шість аркушів сутностей: `clients`, `client_profiles`, `contacts`, `interactions`, `grants`, `applications`. Додатково `_crm_control` і `_crm_journal`. Налаштування не додає демонстраційних клієнтів. Повтор перевіряє заголовки, відновлює незавершену операцію і зберігає дані. Несумісні таблиці не мігруються й не очищаються.

Аркуші сутностей мають колонки `id`, `client_id`, `version`, `data_json`. Повний типізований запис міститься в JSON, включно з датами, сумами, списками та `deleted_at`. Це фізичний формат М2.5; він не є готовою таблицею для ручного редагування чи імпорту. JSON запобігає перетворенню тексту на формули й дат/номерів на інший формат Sheets; UUID та версія дублюються окремо для перевірки цілісності.

- Профіль відокремлений від клієнта; його UUID збігається з UUID клієнта в окремому просторі ключів таблиці, `client_id` обов’язковий. Версія профілю дорівнює версії клієнта.
- Для кожної заявки створюється окремий грантовий запис із тим самим UUID у таблиці `grants`; `grant_id` стабільний. Однакові назви **не об’єднують** конкурси. Окреме управління конкурсами залишається М3.
- `amount` М2 відображається в `requested_amount`, а назва/донор/дедлайн — в `grants`. Невідома сума залишається `null`.
- Контакти й взаємодії мають версію 1 при додаванні. Як у М2, їхній публічний API лише додає записи; історія не редагується й не видаляється. Зміни досьє й заявок зберігаються в попередніх знімках журналу.
- UUID генерує `Utilities.getUuid`; номер клієнта виділяється всередині заблокованої транзакції. Зв’язки не залежать від номера рядка. Видалення клієнта не руйнує історію та залежні записи.

## Транзакції, конфлікти та збої

Усі читання, записи, налаштування й відновлення беруть `LockService.getScriptLock()` з очікуванням до 10 секунд. Перед звільненням блокування записи примусово завершуються через `SpreadsheetApp.flush()`. Один файл бази обслуговує **один** Apps Script-проєкт: ScriptLock не координує різні проєкти або ручне редагування таблиці.

Послідовність запису:

1. Відновити попередню `pending`-операцію, прочитати та перевірити поточний стан.
2. Перевірити `requestId` і відбиток запиту. Для повтору повернути збережений результат.
3. Перевірити очікувану ревізію бази; зміна клієнта/заявки також перевіряє версію запису в `CrmService`.
4. Змінити копію, перевірити зв’язки, UUID, версії та розмір. Зберегти повний наступний стан у нових рядках журналу. Частини мають префікс `j:` і до 15 000 Unicode-символів, без розриву сурогатних пар.
5. Виконати `flush`, перечитати журнал і перевірити SHA-256. Записати одним значенням керівну комірку з попереднім `committed` і новим `pending`.
6. Оновити аркуші сутностей, виконати `flush`, замінити керівну комірку на `committed` без `pending`.

До появи `pending` збій залишає попередній стан; осиротілі фрагменти журналу ігноруються. Після появи `pending` наступний запит ідемпотентно завершує всю операцію. Тому помилка або обрив відповіді **не означає**, що запис скасовано: клієнт повторює точно той самий об’єкт запиту з тим самим UUID. Інше тіло з тим самим UUID відхиляється. Зміна порядку полів JSON також змінює відбиток: зберігайте оригінальний об’єкт до підтвердження.

Результати запитів зберігаються у приватному стані бази й не видаляються автоматично. Повтор повертає історичний результат операції, а актуальний стан слід читати новим запитом. Після конфлікту потрібно зберегти текст форми, перечитати дані й сформувати **нову** дію та UUID; примусового перезапису немає.

Пошкоджений журнал або контрольна сума блокують роботу; автоматичного скидання немає. Ручні зміни аркушів при відсутності pending виявляються й не перезаписуються. Під час pending діє завершення запланованого запису: редагувати аркуші напряму заборонено.

## Серверний API

Відповідь: `{ok:true,value:...}` або `{ok:false,code,message}`. Сирі винятки Google, ID, адреси та вміст записів не потрапляють у повідомлення помилок. `CONFLICT` означає конфлікт ревізії/версії; `UNAVAILABLE` — безпечна загальна відмова, включно з доступом, квотами, валідацією чи невідомою дією. Автоматичного циклу повторів немає.

`crmQuery({action,args})` підтримує `listClients`, `listApplications`, `getClient`, `getApplication`, `listRelated`. Відповідь містить `revision` і `result`. Списки мають сторінки по 20 записів, максимум 100; браузер не отримує повного знімка чи журналу. `listRelated` приймає `table`, `client_id`, `page`, `limit`; контакти видаленого клієнта не видаються. Повний стан обробляється лише на сервері.

`crmMutate({requestId,revision,action,args})` підтримує:

| action | args |
|---|---|
| `saveClient` | `input`, необов’язкові `id`, `version` для редагування |
| `saveApplication` | `input`, необов’язкові `id`, `version` |
| `clientAction` | `id`, `action` (`archive`, `restore`, `delete`), `confirmed` для видалення |
| `deleteApplication` | `id`, `confirmed:true` |
| `addRelated` | `table` (`contacts` або `interactions`), `input` |

`revision` обов’язкова навіть для видалення й архівування, де локальний контракт М2 не мав параметра версії. Аргументи не дозволяють обрати іншу таблицю Google, змінити конфігурацію або виконати довільний метод сховища. Адміністративні функції з суфіксом `_` недоступні через `google.script.run`.

## Знімки та відновлення

`snapshot()`/`restore(snapshot)` перевірено на імітації. Відновлення — така сама журнальна транзакція; лічильник клієнтів не зменшується, версії відновлених записів підвищуються, поточні квитанції повторів зберігаються. Старі форми відхиляються. Попередні знімки залишаються в журналі навіть після м’якого видалення; це потрібно врахувати при майбутній політиці строків зберігання.

Приватні серверні обгортки: `backupCrm_()`, `restoreCrm_(snapshot,expectedRevision)`. Вони повертають безпечний конверт відповіді. Значення резервної копії не друкувати через `console.log`/`Logger` і не вставляти в код: воно має залишатися у приватному середовищі. У М2.5 немає кнопки експорту, зовнішнього сховища резервних копій чи щоденного тригера; це залишається М4. Журнал у тому самому файлі не захищає від видалення всього файлу або втрати акаунта.

Якщо вручну змінено проєкції, спершу зберегти приватну копію файла. Лише після перевірки застосувати `repairCrm_(expectedRevision,true)`: він відновлює аркуші з підтвердженого журналу. Невідома ревізія, несумісні заголовки або пошкоджений журнал блокують ремонт. Якщо пошкоджено сам журнал, потрібне відновлення з незалежної приватної копії в окремому тестовому файлі; автоматичного обходу перевірок немає.

## Межі та перевірки

Це консервативний адаптер початкової бази: читає стан цілком на сервері, записує повний знімок і оновлює проєкції. Ліміт стану — 2 000 000 UTF-16 одиниць, JSON одного запису — 45 000, журналу — менше 100 000 рядків. Перевищення відхиляється до pending. Зростання журналу потребує окремо погодженого обслуговування; автоматичного видалення історії немає. Квоти Google можуть спрацювати раніше; вони дають відмову або pending для повторного завершення, а не мовчазний успіх. Навантаження на сотнях клієнтів і реальні квоти ще не виміряні.

Локальна перевірка: `npm test`, `npm run build`, `git diff --check`. Тести зібраного `.gs` виконуються в Node VM без CommonJS, із підставними SpreadsheetApp, LockService, Utilities, Session і PropertiesService. Це перевірка інтеграції коду, а не підтвердження роботи реального середовища Google.

48 автоматичних тестів успішні на Node.js 24.19.0, включно з усіма попередніми М1/М2. Нові перевірки охоплюють CRUD, зв’язки, нормалізацію, повторне налаштування, ідемпотентність, застарілі зміни, зайняте блокування, кожну межу запису/flush до й після застосування, повторний збій recovery, пошкоджені дані й втрачені метадані, відновлення знімка, формули як текст, розміри комірок та відмову сторонній ідентичності. Реальний вхід власника/стороннього акаунта й продуктивний `ACCEPTANCE.md` залишаються непроведеними до окремого дозволу.
