# CRM 1.4 — контрольоване підключення Google Apps Script до GitHub

**Мета:** не копіювати Apps Script файли вручну при наступних оновленнях і **не чіпати робочу CRM 1.3** до перевірки та окремого дозволу власника.

## Поточний стан

У `.github/workflows/apps-script-staging.yml` підготовлено **контрольоване завантаження коду тільки в окремий тестовий Apps Script** (без створення WebApp deployment і без змін робочої CRM).

- Staging запускається через `push` **лише** у гілку `codex/crm-1-4-workflow-upgrade` зі зміною самого `.github/workflows/apps-script-staging.yml` і повідомленням коміту, що починається з `staging: run CRM 1.4`. Звичайні коміти та злиття PR самі по собі не запускають цей процес.
- 05.11.2026 контрольований staging workflow успішно завантажив код у тестовий Apps Script. Це **не** означає, що пройдено приймання реального Google Calendar.
- Усі тести, збірка і `verify-cloud-release` виконуються **до** будь-якого підключення Google.
- Обов'язкові три secret у GitHub Environment `crm-staging`:
  - `CLASPRC_JSON` — закритий JSON з OAuth-даними **цього власника** після одноразового `clasp login`.
  - `CRM_STAGING_SCRIPT_ID` — ідентифікатор **окремого тестового** Apps Script проєкту.
  - `CRM_PRODUCTION_SCRIPT_ID` — ідентифікатор чинного робочого проєкту **лише для перевірки нерівності**.
- Два Script ID обов'язково різні; за відсутності або збігу скрипт припиняє виконання. Контроль погодженого тестового Script ID у workflow здійснюється через SHA-256, без відкритого ID у поточному файлі. Попередні коміти Git залишаються доступними, тому не можна вважати раніше оприлюднений ID секретним.
- `clasp push --force` оновлює тільки код тестового Script, не створює нових webapp deployments і не змінює наявні налаштування Script Properties, зокрема `CRM_SPREADSHEET_ID` і `CRM_OWNER_EMAIL`.
- Секрети ніколи не комітити до публічного GitHub, не надсилати в ChatGPT, повідомлення чи скриншоти. Не виводити OAuth JSON у логи.
- `.clasp.json`, `.clasprc.json` та `dist/` ігноруються Git.

## Одноразове налаштування (власник акаунта)

### Крок 1. Дозволити Apps Script API

Відкрити `https://script.google.com/home/usersettings` в Google-акаунті власника CRM. Увімкнути **Google Apps Script API — On** / **Дозволити Apps Script API**. Змінюються лише настройки API, CRM та клієнтські дані не зачіпаються.

### Крок 2. Створити тестовий Apps Script

Створити **новий порожній** Google Apps Script проєкт (не копіювати секрети або дані чинної CRM). Записати його Script ID. Поточний продуктивний проєкт лишити без змін. Продуктивний Script ID взяти у вкладці `Project Settings` чинного проєкту.

### Крок 3. Одноразова OAuth-авторизація clasp

На довіреному пристрої під власним Google-акаунтом із Node.js 22+:
```sh
npx --yes @google/clasp@3.4.1 login
```
Підтвердити лише необхідні дозволи у вікні Google. Команда створює приватний файл `~/.clasprc.json`. **Ніде не публікувати його.**

У звичайному чаті або в публічному GitHub не передавати цей файл; зберігати його в GitHub Environments як Secret `CLASPRC_JSON`. Якщо OAuth видав помилку, не передавати токени для «діагностики». У деяких акаунтах Google додатково вимагає налаштування OAuth-клієнта.

### Крок 4. GitHub Environment

GitHub → репозиторій CRM → **Settings → Environments → New environment → `crm-staging`**. Налаштувати доступ лише довіреним гілкам/ролям (за можливості потрібен reviewer). У Environment secrets створити **три** секрети, зазначені вище. Не використовувати Variables для токенів.

### Крок 5. Ручний запуск після підтвердженого тестового проєкту

У гілці `codex/crm-1-4-workflow-upgrade` staging запускається лише після push коміту зі зміною цього workflow та повідомленням, що починається з `staging: run CRM 1.4`. GitHub запускає перевірки й завантажує код після звірки погодженого тестового Script ID. Якщо бракує секретів, додайте їх у `crm-staging` і повторіть той самий запуск через **Re-run failed jobs**.

*Це ще не публікація живої CRM і не створення тестових подій в основному Google Calendar.* Для повного e2e необхідні окремі Script Properties із синтетичною Google Sheets, перевірка OAuth Calendar, ручні smoke-тести та контроль резервної копії. `.github/workflows/apps-script-production-stage.yml` уже існує, але звичайний коміт пропускає його завдання. Спеціально дозволений релізний коміт може завантажити **HEAD-код у production Apps Script**, тому його **не створювати до окремого рішення власника після приймання**. Навіть цей процес не оновлює чинний WebApp deployment; його ID та адресу необхідно зберегти.

## Контроль безпеки

1. У публічному GitHub тільки код і синтетичні тести, жодних реальних ідентифікаторів клієнтських даних.
2. При розгортанні не міняємо `CRM_SPREADSHEET_ID` або `CRM_OWNER_EMAIL` продуктивної CRM.
3. `clasp push` сам по собі оновлює HEAD вихідного коду тестового Script, але не опубліковану версію WebApp.
4. У production не використовувати `create-deployment` для існуючої CRM: після приймання потрібно **оновити той самий deployment ID**, щоб не змінилась адреса.
5. Власник має право відкликати OAuth доступ і обнулити GitHub секрети; для екстреного rollback продуктивної версії потрібен попередній номер версії Script deployment.

## Наступні контрольні точки до випуску

- Успішне тестове завантаження коду через `clasp push` не підтверджує авторизацію Calendar у виконуваному Apps Script та не публікує WebApp.
- Перед першою роботою з Google Calendar власник має надати Apps Script дозвіл `https://www.googleapis.com/auth/calendar` та перевірити `crmCalendarCheck`. Ця функція не створює подій.
- Потрібна приватна тестова таблиця Google Sheets лише із синтетичними записами, перевірка браузерного інтерфейсу, ізоляції доступу та відновлення після збоїв.
- Тільки після окремого погодження допустимі синтетичні календарні події в основному календарі власника; інші події не змінюються.
- До production необхідні приватна резервна копія чинної бази, перевірка відновлення на копії та запис поточного deployment ID й версії WebApp. Не виконувати merge чи релізний push без приймання.

## Перевірка ізольованої Google Sheets — тільки читання (05.11.2026)

Через підключений Google Drive знайдено окрему таблицю `CRM_1_4_TEST_DB` та її ранішу резервну копію `CRM_1_4_TEST_DB_BACKUP_before_schema12_2026-11-05`. Ідентифікатори таблиць не копіювати до публічного GitHub.

- У **поточній тестовій** таблиці наявні 12 вкладок, включно з `clients`, `client_profiles`, `contacts`, `interactions`, `applications`, `grants`, `documents`, `partners`, `client_partners`, `_crm_control`, `_crm_journal` і початковим `Аркуш1`.
- Заголовки 9 таблиць сутностей за структурою: `id | client_id | version | data_json`; службові вкладки мають відповідно `control_json` і `chunk`.
- Під час обмеженої **read-only** перевірки у тестовій таблиці виявлено принаймні один запис клієнта й профілю; інші перевірені таблиці можуть бути порожніми. Жодні значення клієнтських записів не розкривати, не копіювати та не публікувати.
- У старішій резервній копії присутня структура до `schema12`; вона **не є доказом** актуального або перевіреного резервного копіювання продуктивної бази.
- **Не підтверджено:** чи саме цю тестову таблицю використовує тестовий Apps Script; фактичну версію журналу та цілісність проєкцій; дозвіл OAuth Calendar у тестовому Apps Script; повний цикл запису/відновлення через Google API.
- На цьому етапі Google Sheets **не змінювалися**. До подальшого запису в тестову базу слід перевірити її прив'язку до окремого Script Properties і підтвердити, що її дані синтетичні.


## Read-only передперевірка зв'язку тестового Apps Script з окремою Sheets (05.11.2026)

Нову функцію `verifyCrmTestSheetConnection` дозволено запускати вручну **лише у тестовому Apps Script CRM 1.4**. Вона не створює подій та не змінює Google Sheets, а звіряє лише технічні заголовки 9 таблиць сутностей і 2 службових таблиць.

**Захисні перевірки:** `ScriptApp.getScriptId()` має збігатися за SHA-256 із **затвердженим окремим staging Script ID**, який також перевіряється в GitHub Actions; чинна авторизація власника має пройти `CrmGateway.authorize`; SHA-256 приватного `CRM_SPREADSHEET_ID` повинен збігатися із зафіксованою перевіреною **окремою** тестовою таблицею `CRM_1_4_TEST_DB`. Ідентифікатори, клієнтські значення, дані журналу та приватні помилки не виводяться і не зберігаються у публічному репозиторії. **`CRM_ENVIRONMENT=test` не потрібне:** `clasp push` не встановлює Script Properties, тож його відсутність не означає, що відкрито production. Прапорець `CRM_ENVIRONMENT` продовжує застосовуватися окремо для діагностики `crmDiagnostics_`, але не для цієї перевірки.

- Успіх: `CRM_TEST_SHEET_OK; entityTabs=9; control=1; journal=1; recordRowsRead=0; writes=0`.
- `TEST_SCRIPT_MISMATCH`: поточний Apps Script **не збігається** з погодженим окремим тестовим Script ID; **не** змінювати налаштування, не запускати міграцію, запис чи синхронізацію.
- `TEST_SHEET_MISMATCH`: Script Properties вказують не на погоджену тестову таблицю; без з'ясування причини **не** запускати міграції, синхронізацію чи запис.
- `SCHEMA_MISMATCH` або `UNAVAILABLE`: перевірити технічні заголовки/доступ у тестовому середовищі, не чіпаючи продуктивні дані.

Ця перевірка **не доводить**, що наявні записи тестової таблиці синтетичні, що правильно працює транзакційний журнал або що CRM синхронізувалася з реальним календарем. Наскрізна синтетична інтеграція UI → RPC → Sheets Repository → Calendar вже покривається локальними тестами з ізольованими замінниками Google API, без запису в особистий Google Calendar. Пряме створення нового Calendar event вимагає окремого дозволу власника.


## Ручна перевірка цілісності ізольованої тестової бази (read-only, 05.11.2026)

Після успіху `verifyCrmTestSheetConnection()` власник може виконати **тільки в ізольованому тестовому Apps Script** функцію `verifyCrmTestDatabaseIntegrity()` (зі списку Run). Вона читає фактичні дані тестової таблиці виключно для локальної перевірки цілісності, але **не виводить вміст записів у журнал і не записує/відновлює/виправляє жодних клієнтських даних**.

Захист від випадкового доступу до production: перевірка SHA-256 **погодженого staging Script ID**, окремого тестового Spreadsheet ID та авторизації власника; ці самі ідентифікатори застосовувалися у read-only перевірці заголовків. Якщо перевірка не проходить, доступ до Google Sheets не відкривається. Функція використовує `SheetsRepository.locked()`, але **не** `read()`, `recover()`, `setup()`, `repairProjection()`, `migrate12()` чи `transaction()`: ці методи можуть записувати й змінювати дані.

Порядок перевірок: поточний control pointer → відсутність `pending` → підтверджений `committed` журнал → контроль SHA-256, парсинг JSON та валідація стану → модель CRM 12 → повна відповідність дев’яти таблиць-проєкцій підтвердженому журналу. **Виявлений `pending` не відновлюється автоматично**. Читання таблиці може охоплювати клієнтські дані тестової БД, тому ніяких значень не копіювати до чату чи публічного GitHub; синтетичність цих даних поки не підтверджено.

Можливі результати у журналі:
- `CRM_TEST_INTEGRITY_OK; schema=2; model=12; projectionTabs=9; dataLogged=0; writes=0` — журнал, контрольна сума і проєкції узгоджені.
- `CRM_TEST_INTEGRITY_FAILED; code=PENDING_TRANSACTION` — наявна незавершена транзакція. Нічого не відновлювати без окремого безпечного плану.
- `CRM_TEST_INTEGRITY_FAILED; code=JOURNAL_INVALID` — перевірка журналу не пройшла.
- `CRM_TEST_INTEGRITY_FAILED; code=PROJECTION_MISMATCH` — таблиці не відповідають підтвердженому журналу; автоматичне виправлення заборонене.
- `CRM_TEST_INTEGRITY_FAILED; code=TEST_SCRIPT_MISMATCH|TEST_SHEET_MISMATCH|SCHEMA_MISMATCH|NO_COMMITTED_JOURNAL|UNAVAILABLE` — контрольована відмова без розкриття приватних подробиць.

Це ще **не** дає дозволу на запис до таблиці, використання її наявних клієнтів у демо, автоматичний `crmCalendarSync()` чи створення подій у Google Calendar. Production CRM 1.3 не змінювати.


## Одноразова синтетична CRUD-перевірка на новій окремій таблиці (05.11.2026)

Для наступного ручного приймання в тестовому Apps Script підготовлено `verifyCrmIsolatedSyntheticCrud()`. **На відміну від попередніх read-only перевірок, вона СТВОРЮЄ нову окрему Google Sheets у приватному Drive власника та записує туди виключно синтетичні дані.** Новий файл має назву, що починається з `CRM_1_4_SYNTHETIC_CRUD_` і закінчується випадковим суфіксом. Таблиця залишається у Drive для приватного аудиту; повторні запуски створюють нові тестові файли, тому запускати функцію **один раз**.

Перед створенням файлу перевіряються:
1. SHA-256 ID затвердженого окремого staging Apps Script.
2. Авторизація власника CRM.
3. SHA-256 `CRM_SPREADSHEET_ID` існуючої `CRM_1_4_TEST_DB`, **без відкриття та зміни** цієї таблиці.

У створеній порожній Google Sheets виконується `setup()` та `migrate12(0,true)`, після чого CRM створює й оновлює **одного вигаданого клієнта**, створює вигадану заявку, контакт і взаємодію з календарною дією `Europe/Istanbul`. Перевіряється узгодженість даних і журналу, скасування календарної дії без синхронізації, архівація/відновлення клієнта і заявки, їхнє м’яке видалення. Це тестує **реальні записи Google Sheets через Apps Script**, але **не** WebApp у браузері та **не** створення Google Calendar events.

Очікуваний рядок: `CRM_SYNTHETIC_CRUD_OK; scratchCreated=1; schema=12; clients=1; contacts=1; applications=1; interactions=1; calendarEvents=0; originalTestSheetWrites=0`. У разі збою: `CRM_SYNTHETIC_CRUD_FAILED` з безпечним кодом; не намагайтеся виправляти чи очищувати чужі файли, передайте лише код. Якщо помилка виникла після створення окремої синтетичної таблиці, вона може залишитися у Drive для діагностики.

**Межа доказовості:** успішна ручна перевірка означає роботу CRM 1.4 CRUD зі справжнім SpreadsheetApp на **новому синтетичному файлі**. Наявні дані `CRM_1_4_TEST_DB` не змінюються, робоча CRM 1.3 і особистий Google Calendar не зачіпаються. Для реального CRM → Calendar потрібен інший погоджений тест, перед production — резервна копія та відновлення на копії.
