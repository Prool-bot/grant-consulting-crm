# CRM 1.4 — контрольоване підключення Google Apps Script до GitHub

**Мета:** не копіювати Apps Script файли вручну при наступних оновленнях і **не чіпати робочу CRM 1.3** до перевірки та окремого дозволу власника.

## Поточний стан

У `.github/workflows/apps-script-staging.yml` підготовлено **лише ручну публікацію коду в окремий тестовий Apps Script** (без створення webapp deployment та без змін продуктивного проєкту).

- Запуск можливий тільки із гілки `main`, після появи workflow на основній гілці; поки CRM 1.4 живе в **draft PR**, він не запускається.
- Усі тести, збірка і `verify-cloud-release` виконуються **до** будь-якого підключення Google.
- Обов'язкові три secret у GitHub Environment `crm-staging`:
  - `CLASPRC_JSON` — закритий JSON з OAuth-даними **цього власника** після одноразового `clasp login`.
  - `CRM_STAGING_SCRIPT_ID` — ідентифікатор **окремого тестового** Apps Script проєкту.
  - `CRM_PRODUCTION_SCRIPT_ID` — ідентифікатор чинного робочого проєкту **лише для перевірки нерівності**.
- Два Script ID обов'язково різні; за відсутності або збігу скрипт припиняє виконання.
- `clasp push --force` оновлює тільки код тестового Script, не створює нових webapp deployments і не змінює наявні налаштування Script Properties, зокрема `CRM_SPREADSHEET_ID` і `CRM_OWNER_EMAIL`.
- Секрети ніколи не комітити до публічного GitHub, не надсилати в ChatGPT, повідомлення чи скриншоти. Не виводити OAuth JSON у логи.
- `.clasp.json`, `.clasprc.json` та `dist/` ігноруються Git.

## Одноразове налаштування (власник акаунта)

### Крок 1. Дозволити Apps Script API

Відкрити `https://script.google.com/home/usersettings` в Google-акаунті власника CRM. Увімкнути **Google Apps Script API — On** / **Дозволити Apps Script API**. Змінюються лише настройки API, CRM та клієнтські дані не зачіпаються.

### Крок 2. Створити тестовий Apps Script

Створити **новий порожній** Google Apps Script проєкт (не копіювати секрети або дані чинної CRM). Записати його Script ID. Поточний продуктивний проєкт лишити без змін. Продуктивний Script ID взяти у вкладці `Project Settings` чинного проєкту.

### Крок 3. Одноразова OAuth-авторизація clasp

На довіреному пристрої під власним Google-акаунтом із Node.js 22+:
```sh
npx --yes @google/clasp@3.4.1 login
```
Підтвердити лише необхідні дозволи у вікні Google. Команда створює приватний файл `~/.clasprc.json`. **Ніде не публікувати його.**

У звичайному чаті або в публічному GitHub не передавати цей файл; зберігати його в GitHub Environments як Secret `CLASPRC_JSON`. Якщо OAuth видав помилку, не передавати токени для «діагностики». У деяких акаунтах Google додатково вимагає налаштування OAuth-клієнта.

### Крок 4. GitHub Environment

GitHub → репозиторій CRM → **Settings → Environments → New environment → `crm-staging`**. Налаштувати доступ лише довіреним гілкам/ролям (за можливості потрібен reviewer). У Environment secrets створити **три** секрети, зазначені вище. Не використовувати Variables для токенів.

### Крок 5. Ручний запуск після підтвердженого тестового проєкту

У гілці `codex/crm-1-4-workflow-upgrade` staging запускається лише після push коміту зі зміною цього workflow та повідомленням, що починається з `staging: run CRM 1.4`. GitHub запускає перевірки й завантажує код після звірки погодженого тестового Script ID. Якщо бракує секретів, додайте їх у `crm-staging` і повторіть той самий запуск через **Re-run failed jobs**.

*Це ще не публікація живої CRM і не створення тестових подій в основному Google Calendar.* Для повного e2e необхідні окремі Script Properties із синтетичною Google Sheets, перевірка OAuth Calendar, ручні smoke-тести і лише потім підготовка окремого захищеного production workflow із збереженням чинного webapp deployment ID.

## Контроль безпеки

1. У публічному GitHub тільки код і синтетичні тести, жодних реальних ідентифікаторів клієнтських даних.
2. При розгортанні не міняємо `CRM_SPREADSHEET_ID` або `CRM_OWNER_EMAIL` продуктивної CRM.
3. `clasp push` сам по собі оновлює HEAD вихідного коду тестового Script, але не опубліковану версію WebApp.
4. У production не використовувати `create-deployment` для існуючої CRM: після приймання потрібно **оновити той самий deployment ID**, щоб не змінилась адреса.
5. Власник має право відкликати OAuth доступ і обнулити GitHub секрети; для екстреного rollback продуктивної версії потрібен попередній номер версії Script deployment.
