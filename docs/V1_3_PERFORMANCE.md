# CRM 1.3 — оптимізація швидкості

Це продовження Draft PR #9, без розгортання чи доступу до робочих Google-ресурсів. Нові OAuth scopes і залежності не потрібні. Модель 12, схема Sheets 2, аркуші, заголовки та формат журналу/квитанцій незмінні.

## Що змінено

- `crmQuery({action:'bootstrap'})` повертає всі сім колекцій однієї перевіреної ревізії одним RPC. Квитанції та внутрішні метадані журналу/міграції не передаються. Чинний ліміт знімка 2 млн символів збережено; пагінований `listData` лишається доступним для старих клієнтів.
- Новий клієнт передає `sync:true` у записі. Під тим самим ScriptLock сервер формує відповідь із результатом, базовою/новою ревізіями, sequence та зміненими записами. Браузер валідує цілий кандидат стану й атомарно замінює його. Незмінні колекції не передаються повторно. Зміни `deleted_at` також синхронізуються; залежні контакти/документи/заявки приховуються з перегляду.
- При повторі requestId повертається первісний результат та **актуальний повний стан** під lock. Це враховує записи з іншої вкладки, які могли відбутися після втрати відповіді. Квитанція не роздувається копією стану. Інше тіло з тим самим UUID відхиляється, як раніше.
- Якщо дельту неможливо застосувати, виконується один bootstrap. При його помилці зберігаються acknowledged/pending; повтор виконує читання, а не новий запис. Конкурентні reload/mutate в одному Service блокуються; стара відповідь не відкочує ревізію.
- `recover()` як і раніше перевіряє контрольну суму журналу, модель, заголовки та всі рядки всіх аркушів. Заголовок і дані читаються одним діапазоном. Кешу між серверними операціями немає: ручні зміни Sheets та пошкодження журналу виявляються при наступному читанні.
- Звичайний commit записує лише змінені проєкції аркушів, порівнюючи їх із перевіреним станом під тим самим lock. Повний журнал, flush і контрольні покажчики збережено. Відновлення pending, ремонт і міграція продовжують проєктувати повний стан.
- Каталог групує контакти за client_id за один прохід; видимі зв’язки перевіряються через Set. Пошук має затримку 150 мс після введення; таймер не малює покинутий екран. У remote-сесії кешуються до 30 результатів сторінок/фільтрів, кеш скидається після встановлення стану та щохвилини для динамічних дат. Кеш лише в пам’яті поточної вкладки.

## Порівняння до/після

Команда `node scripts/benchmark-crm.js` порівнює remote/adapter/gateway із коміту `130d1e7` з поточними. Потрібна історія Git із цим комітом. Використовується лише FakeSheets: 250 вигаданих клієнтів і по одному запису в інших колекціях. Спільна поточна бізнес-логіка в обох прогонах ізолює ефект транспорту й адаптера. Немає мережевих запитів або доступу до Google.

| Показник | Завантаження до → після | Збереження клієнта до → після |
|---|---:|---:|
| RPC | 9 → 1 | 10 → 1 |
| Читання діапазонів | 180 → 11 | 202 → 13 |
| Записи + flush | 0 → 0 | 16 → 9 |
| Байти відповідей | 40 925 → 40 514 | 41 324 → 655 |
| Час локальної імітації, мс (один прогін) | 25,51 → 3,31 | 29,83 → 9,02 |

Час локальної імітації не прогнозує час Google Apps Script: він не включає мережу, холодний старт чи квоти. Лічильники RPC/читань перевіряються тестами; абсолютні мілісекунди не є нестабільним порогом CI. Якщо кожна колекція вкладається в 100 записів, початкові 7 RPC скорочуються до 1, збереження 8 → 1.

У браузері `crm.metrics` містить останні 50 вимірювань `{operation,durationMs,ok}` для reload та записів. Значення зберігаються тільки в пам’яті, без текстів/ID клієнтів, аргументів запитів чи помилок. Для ручного порівняння на **окремій тестовій копії після дозволу**: відкрити консоль, виконати `console.table(crm.metrics)`, порівняти кілька холодних/теплих запусків і збережень з однаковим набором синтетичних даних. Час запису охоплює RPC і застосування/відновлення стану; серверні Google-часи окремо не виміряні.

## Перевірки й межі

`npm test`, `npm run build`, `node scripts/verify-cloud-release.js`, `node scripts/benchmark-crm.js`.

Нові тести перевіряють кількість RPC і читань, усі види записів, еквівалентність дельти повному стану, кеш, приховування залежностей, чужі зміни між записом і повтором, відмову при пошкодженнях навіть після повторного читання, конкурентні запити, збій ДО/ПІСЛЯ кожної межі запису/flush та атомарність застосування відповіді. Зібраний Apps Script перевіряється для bootstrap/sync і відмови чужій ідентичності. Наявні тести резервних копій, міграції, ревізій, ідемпотентності й приватного доступу залишаються.

Повний журнал досі дописується при кожній зміні, а всі проєкції перевіряються на кожну серверну операцію. Це свідомо збережені гарантії безпеки; їхня вартість зростає з розміром бази. Новий клієнт і сервер слід випускати разом лише за окремим дозволом. Старі клієнтські запити без sync зберігають попередній контракт. Продуктивна CRM 1.2 не змінювалась.

Поетапна серверна діагностика: [увімкнення лише в тестовому середовищі, формат без приватних даних і план подальшої оптимізації](V1_3_DIAGNOSTICS.md). За замовчуванням вимкнена; продуктивні властивості й розгортання не змінюються.

Подальша оптимізація перевірки та запису рядків: [результати для 3/100/250/1000 клієнтів](V1_3_PROJECTIONS.md).
