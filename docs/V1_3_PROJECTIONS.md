# CRM 1.3 — перевірка і частковий запис проєкцій

База порівняння: d5af840 (попередній стан Draft PR №9). Вхідні серверні заміри власника: читання repository_total 2185 мс / sheets_verify 1718 мс; запис repository_total 12747 мс / sheets_verify 5859 мс / sheets_update 4563 мс / flush 1251 мс (4 виклики), journal_read 368 мс, lock_wait 128 мс. Вкладені durationMs не підсумовуються: flush частково входить у sheets_update.

## Зміни

- verifyProjection читає заголовок і всі заповнені рядки кожного з дев’яти аркушів через getDataRange().getValues(), без окремого getLastRow. Перевірка чотирьох колонок схеми повна; сторонній рядок за очікуваною межею, навіть лише в п’ятій колонці, не приховується. Додаткові колонки в межах наявних рядків, як і раніше, не належать проєкції. Широкі сторонні колонки можуть збільшити обсяг читання; цей спосіб не гарантує прискорення на довільно зміненій вручну базі.
- Об’єкти аркушів кешуються лише на час locked(). Кеш очищається після успіху, помилки й невдалого lock. Значення комірок та результат перевірки між операціями не кешуються.
- project порівнює кожен нормалізований рядок із перевіреним попереднім станом під тим самим lock. Сусідні зміни записуються одним setValues; незмінні рядки не переписуються. Додавання розширює місткість лише за потреби; редагування і м’яке видалення зберігають позиції. Перестановка/вставка всередині масиву перезаписує відповідні позиції. Скорочення при відновленні знімка очищає лише залишковий хвіст проєкції за чинним протоколом; аркуші та журнал не видаляються.
- Recovery не покладається на старі позиції: після pending відновлює всі проєкції повністю. Контрольна сума нового журналу, requestId, ревізії, ScriptLock та порядок журнал → pending → проєкції → committed незмінні. У звичайному commit залишено 4 flush.
- Модель 12, схема 2, PROFILE, формат журналу, CRM 1.2, OAuth і конфігурація приватного доступу незмінні. Нових залежностей немає.

## Пакетне читання: дослідження

[Sheet.getDataRange](https://developers.google.com/apps-script/reference/spreadsheet/sheet#getDataRange()) повертає прямокутник усіх даних аркуша. Це використано для одного читання на аркуш без окремого визначення останнього рядка. Це не один мережевий запит на всі аркуші, і внутрішню кількість RPC SpreadsheetApp локальні лічильники не вимірюють.

[RangeList](https://developers.google.com/apps-script/reference/spreadsheet/range-list) не має спільного getValues; getRanges із подальшими читаннями не дає доведеного скорочення. [Sheets API values.batchGet](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/batchGet) може читати кілька діапазонів, але потребує іншого адаптера та налаштування сервісу, перевірки типів/порожніх клітин і меж. У цьому сумісному оновленні його не додано. Альтернатива без нового сервісу — реалізоване читання прямокутника кожного аркуша.

Запуск: `node scripts/benchmark-projections.js`. Лише вигадані клієнти; редагування catalog_note і збільшення version одного клієнта. Через version змінюється також рядок client_profiles. Еталонні методи проєкцій із d5af840 зафіксовано в tests/helpers/projection-benchmark.js, тому порівняння працює також у shallow checkout CI без мережі.

При завантаженні записів і flush немає; getLastRow 9 → 0, getSheetByName 11 → 11. При збереженні getLastRow 12 → 1, getSheetByName 18 → 11, getMaxRows 3 → 1. Збережені 13 читань включають 9 проєкцій, 2 читання control і 2 читання журналу. П’ять записів — журнал, два control і два змінені діапазони проєкцій. Повний журнал продовжує зростати з розміром бази.

Кількість записів діапазонів може збільшитись для багатьох рознесених змін; суміжні зміни групуються, а recovery записує цілі проєкції. Наведені числа не є обіцянкою скорочення Google-часу в тій самій пропорції. Нових реальних вимірювань і змін робочих Google-ресурсів під час розробки немає.

## Перевірки та подальші заміри

Автоматичні тести: чотири розміри баз; суміжні й рознесені зміни; додавання/редагування/м’яке видалення; перестановка, скорочення та порожній стан; усі аркуші й зайві рядки; кожна межа запису/flush ДО та ПІСЛЯ ефекту, включно з розширенням місткості й очищенням синтетичного хвоста; повторні збої самого recovery; ідемпотентні квитанції. Чинні тести ревізій, доступу, журналу, резервних копій і міграції залишаються обов’язковими.

Діагностика з [V1_3_DIAGNOSTICS.md](V1_3_DIAGNOSTICS.md) збережена. Після окремого дозволу на тестове середовище порівняти медіану й максимум sheets_verify, sheets_update та repository_total на однакових синтетичних даних; перевірити flush.calls=4 для звичайного запису. До/після запускати з однаковими прапорцями, окремо холодні/теплі операції та повтори requestId. Жодних клієнтських даних чи Google ID у звітах.

Результат локальних перевірок: npm test — 121/121; npm run build — успішно; node scripts/verify-cloud-release.js — приватна конфігурація підтверджена.

Остаточне рішення після реальних замірів: стандарт bounded_range. Наведені вище лічильники lastRows для getDataRange є історичними; тепер читання має 9 getLastRow, запис — 10. Частковий запис незмінний. Див. [інструкцію випуску](V1_3_RELEASE.md).
