# CRM 1.0: розгортання лише для власника

Завершений обсяг: клієнти, досьє, наявні контакти/історія, грантові заявки; пошук, фільтри, групування та кольорові статуси. Видалення м’яке: записи зберігаються в базі з `deleted_at`, залежні заявки видаленого клієнта приховані. Архів заявок відкривається перемикачем у реєстрі; відновлення — у формі заявки. Архів клієнтів — фільтр статусу каталогу. Грантові реквізити записуються разом із заявкою.

Жодних додаткових бібліотек чи платних компонентів. Gmail, Calendar, Drive API та ШІ не підключені. Таблиця Google Sheets потрібна як база, але керування файлами Drive не реалізоване.

## Коротке розгортання

Ця інструкція призначена власнику. Агент не створював Google-ресурсів і не публікував застосунок.

1. Локально виконати `npm test` і `npm run build` (Node.js 22+). Готові чотири файли — у `dist/apps-script`.
2. Після рішення власника створити порожню приватну Google-таблицю `CRM_DB_TEST` та приватний Apps Script-проєкт у своєму особистому акаунті. Не додавати співредакторів.
3. Скопіювати `Code.gs`, `Server.gs`, HTML-файл `Index.html` (у редакторі назва `Index`) та `appsscript.json`. Показ маніфесту вмикається в налаштуваннях проєкту. Не копіювати каталог `dist/local`.
4. У Script Properties приватно задати `CRM_OWNER_EMAIL` (власна адреса), `CRM_SPREADSHEET_ID` (ID тестової таблиці), `CRM_ENABLED=true`. Значення не вставляти в код чи Git.
5. Запустити `setupCrm_` у редакторі. Авторизувати лише два дозволи: `spreadsheets` — читання/запис таблиці за ID; `userinfo.email` — перевірка власника. Переконатися, що створено 8 аркушів; повторний запуск не створює дублів. База початково порожня.
6. Deploy → New deployment → Web app: виконання як користувач, який відкриває застосунок (`USER_ACCESSING`); доступ **лише собі** (`MYSELF` / Only myself). Якщо ця комбінація недоступна, не розширювати доступ — зупинити розгортання та перевірити налаштування акаунта. Не обирати Anyone, Anyone with link чи Domain.
7. Відкрити отриманий `/exec` URL: має з’явитися порожній реєстр. Створити вигаданого клієнта, потім заявку. Для оновлень коду завантажити нову збірку та вибрати нову версію в Manage deployments.

Маніфест не гарантує права фактичного розгортання: перевірити їх у діалозі публікації. Офіційна документація: [режими вебзастосунку](https://developers.google.com/apps-script/manifest/web-app-api-executable), [асинхронний HTML Service RPC](https://developers.google.com/apps-script/guides/html/communication).

## Приймання до реальних даних

- [ ] Власник відкриває CRM з комп’ютера та телефона; інший акаунт і анонімний браузер не бачать сторінки чи даних. Проєкт і таблиця приватні; переглянуто SECURITY.md.
- [ ] На вигаданих клієнтах і заявках: створити, редагувати, перезавантажити сторінку, перевірити збереження, архівувати, відновити, м’яко видалити.
- [ ] Пошук, фільтри, сортування, групування й кольори працюють; архівні заявки видно тільки при виборі архіву.
- [ ] На 360 px форми доступні, горизонтально прокручується лише таблиця.
- [ ] Дві вкладки: застаріле збереження відхиляється. Скопіювати текст форми, перейти до реєстру, натиснути «Оновити дані», повторно відкрити запис і застосувати зміни.
- [ ] При обриві з’єднання форма залишається. Не закривати вкладку; натиснути «Перевірити / повторити початковий запис». Повторюється збережений запит з тим самим UUID, незалежно від пізніших змін полів. Після підтвердження екран показує серверні дані; незбережені пізніші правки слід попередньо скопіювати.
- [ ] Створити приватну ручну копію тестової таблиці засобами Google Sheets та перевірити відкриття копії в окремому тестовому проєкті з тими самими файлами/властивостями. Перед реальними даними визначити порядок регулярного резервування. Автоматичного бекапу у Drive немає.

## Виконані локальні перевірки та межі

`npm test`: тести бізнес-валідації, серверного доступу, CRUD, архівування, повторного відкриття, пагінації, конфліктів, втрачених відповідей, квот, часткових записів, резервних знімків і відновлення на імітації Sheets. Збірка перевіряє синтаксис усіх вбудованих скриптів, відсутність демоданих та зовнішніх ресурсів, закритий маніфест і видачу Index тільки після авторизації.

Локальний браузерний сценарій перевірено в Edge на ширинах 1440 і 360 px; скриншоти переглянуто. Фактичний Google OAuth і поведінка розгорнутого HTML Service залишаються ручним прийманням власника. Звіт оновлення клієнтів: [V1_CLIENTS_UI.md](V1_CLIENTS_UI.md).

Дані читаються сторінками по 100 записів з однаковою ревізією, потім зберігаються лише в пам’яті вкладки для пошуку/групування. Продуктивна збірка не читає localStorage і не переносить локальні демодані. Оновлення — при відкритті, після кожного запису та кнопкою реєстру; фонового опитування немає. Пряме редагування службових аркушів заборонене: вони захищені перевірками цілісності М2.5. Застосовуються квоти Google та обмеження розміру журналу адаптера; це персональна база, а не необмежене сховище.

Непідтверджений запит зберігається лише в пам’яті вкладки. Якщо її примусово закрити після збою, спочатку відкрити CRM та перевірити результат запису, перш ніж створювати його повторно. Браузер попереджає про вихід, але не гарантує збереження при аварійному завершенні.
