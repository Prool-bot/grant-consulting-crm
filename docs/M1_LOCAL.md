# М1 — локальний каркас

## Межі реалізації

М1 не підключає жодного Google-сервісу і не потребує OAuth. Немає мережевих запитів, зовнішніх шрифтів, бібліотек, аналітики, localStorage або реальних даних. Залежностей npm немає; використано стандартні можливості Node.js та браузера. Встановлювати пакети не потрібно.

- `source/server` — закритий вхід `.gs` і маніфест без scopes.
- `source/shared` — чисті валідатори, UUID, пошук і правила статусів.
- `source/adapters` — контракти сховища та календаря, реалізації лише в пам’яті; Google-адаптер завжди відмовляє.
- `source/web` — українські HTML/CSS/JS та явно вигадані приклади.
- `scripts` — автономна збірка і сервер лише на loopback.
- `tests` — вбудований тестовий runner Node.js, жодного доступу до Google.
- `config/clasp.example.json` — шаблон без справжнього script ID.
- `dist` — згенеровані локальні файли, виключені з Git.

## Запуск

Потрібен Node.js 22 або новіший. У корені репозиторію:

```sh
npm test
npm run build
npm start
```

Відкрити `http://127.0.0.1:4173`. Зупинити сервер: Ctrl+C. Альтернатива після збірки — відкрити `dist/local/index.html` у браузері.

Екрани: головна, каталог із пошуком/фільтрами, порожня картка з перевіркою полів, демонстраційне досьє, завдання з фільтром періоду, гранти. Дата демонстрації фіксована: 12.10.2026, Europe/Kyiv. Це не актуальний перелік конкурсів. Невідомі суми не перетворюються на нуль.

Повного CRUD, збереження форм, контактів, історії, заявок, документів, фінансів і підбору грантів ще немає. Вкладки цих модулів чесно показують порожній стан. Це межа М1, а не реалізація М2–М4.

## Адаптери й перевірки

MemoryStorage створює 14 логічних таблиць. Повторна ініціалізація не дублює записи і не перезаписує наявні; ключ `id`, для settings — `key`. Дані копіюються на межі адаптера. Ініціалізація й відновлення атомарні в пам’яті. Знімок — допоміжний контракт тестового адаптера, а не продуктивний бекап.

MemoryCalendar моделює upsert/cancel за стабільним ключем синхронізації; повторне оновлення зберігає event ID. Це не реалізація синхронізації з Google, квот чи мережевих повторів. Їхні тести потрібні на відповідних етапах.

UUID створює стандартний crypto.randomUUID у локальному браузері/Node. Майбутній серверний генератор Apps Script має використовувати окрему реалізацію; зараз shared JS працює в клієнтському HTML, а не в `.gs`.

## Майбутнє підключення clasp — лише після окремого дозволу

1. Перевірити актуальну офіційну інструкцію, версію та ліцензію clasp за посиланням у DEPLOYMENT.md. У М1 clasp не встановлюється і не запускається.
2. Авторизувати потрібний особистий акаунт; токени залишаються поза репозиторієм. Не друкувати їх у лог.
3. Після окремого дозволу створити приватний тестовий Apps Script проєкт. Скопіювати `config/clasp.example.json` у локальний `.clasp.json`, замінити заповнювач приватним script ID. Файл ігнорується Git.
4. Виконати локальну збірку, перевірити вміст `dist/apps-script` і лише тоді погодити завантаження. Збірка містить автономний `Index.html`, але `doGet` навмисно його не відкриває.
5. До відкриття вебкабінету реалізувати серверну перевірку власника та перевірити відмову сторонньому акаунту. Не публікувати з Anyone/Anyone with link. Scopes обґрунтовуються окремо для погоджених інтеграцій.

## Що залишається відкритим

Перевірено локально: 12/12 автоматичних тестів, збірка, синтаксис клієнтського JS, `git diff --check`, правила `.gitignore`. У браузері перевірено пошук, помилку порожньої форми та успішну валідацію, приховування ЄДРПОУ для фізособи. Усі п’ять екранів перевірено при ширині 360 px: горизонтального переповнення немає. Скриншоти: `screenshots/m1-desktop.png`, `screenshots/m1-mobile.png` — лише вигадані дані. Перевірка типових шаблонів токенів і реальних Google ID в нових текстових файлах збігів не виявила; це не замінює ручного огляду безпеки перед продуктивним використанням.

- Ініціалізація справжніх Sheets і перевірка доступу власника не виконані: вони суперечили б локальним межам поточного завдання.
- Перевірка на фізичному телефоні, клавіатурна доступність і приймання власником.
- Повний перелік ACCEPTANCE.md — майбутні етапи; застосунок не готовий до реальних даних чи продуктивного розгортання.
- PR можна створити з локальної гілки після окремого рішення про push; у цьому завданні всі зміни залишаються локально.
