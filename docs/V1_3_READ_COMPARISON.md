# CRM 1.3 — реальне A/B-порівняння читання

Власник повідомив 6769, 4996 і 3974 мс після переходу на getDataRange: середнє 5246,3 мс проти попередніх приблизно 3990 мс (+31,5%). Це регресія спостережуваного загального часу; три непарні вимірювання не доводять, що причиною є саме метод читання. sheets_verify залишається головним кандидатом.

## Реалізація і локальний результат

Рішення 22.10.2026: типовий режим bounded_range в усіх середовищах. Контрольні заміри власника: data_range 2063 мс, bounded_range 1351 мс, без помилок; скорочення 712 мс (34,5%). Подальше порівняння для випуску не потрібне. Лише за CRM_ENVIRONMENT=test та CRM_DIAGNOSTICS_ENABLED=true властивість CRM_PROJECTION_READ_MODE дозволяє вибрати data_range або bounded_range. Невідоме непорожнє значення в тестовому середовищі відхиляється; відсутнє означає bounded_range. У production перемикач ігнорується. Параметри RPC його не змінюють.

| Спосіб | Читання діапазонів за read | getLastRow | Колонки проєкцій | Записи / flush |
|---|---:|---:|---|---:|
| data_range | 11 | 0 | Усі заповнені; порівнюються A:D | 0 / 0 |
| bounded_range | 11 | 9 | Лише A:D, до останнього заповненого рядка всього аркуша | 0 / 0 |

Числа підтверджено синтетичними тестами для 0/3/100/250/1000 клієнтів, включно з широким аркушем. Для 1000 клієнтів і заповненої AN1 перший метод читає 1001×40 комірок clients, другий — 1001×4. На стандартному аркуші з чотирма колонками обсяг однаковий. Це не вимірювання часу Google: зменшення явних викликів не гарантує зменшення затримки через внутрішнє кешування сервісу.

Обидва способи відхиляють змінені заголовки/дані, відсутні рядки, зайві рядки у A:D і рядки з даними лише за межами D. Додаткові колонки в межах наявних рядків, як і раніше, не належать проєкції. Частковий запис, журнал, контрольні суми, ревізії, requestId, recovery, схема 2 й модель 12 не змінені.

## Збережена інструкція необов’язкового тестового перемикання

Виконувати власнику лише на вже підготовленому окремому тестовому Apps Script і синтетичній базі після окремого дозволу на перенесення коду. Цей PR нічого не переносить і не розгортає. Нових OAuth scopes або сервісів немає. Не ставити тестові прапорці на робочому проєкті.

1. У тестових Script Properties встановити CRM_ENVIRONMENT=test, CRM_DIAGNOSTICS_ENABLED=true, CRM_PROJECTION_READ_MODE=data_range. Решту приватної конфігурації не змінювати. Переконатися, що тестова база завершила транзакції, без pending.
2. В редакторі вручну виконати benchmarkCrmRead_. Вона авторизує власника, отримує ScriptLock, читає control і журнал, перевіряє checksum/модель та всі проєкції. Не повертає даних, нічого не записує, не викликає flush. Якщо є pending — завершується помилкою без recovery. Не використовувати setup/repair/restore для порівняння.
3. Зберегти лише JSON crm_repository_timing із Executions. Нове поле projectionReadMode має значення data_range або bounded_range. Етапи й числові поля збережені; персональні дані, назви, ID та тексти помилок не додаються. Помилки середовища з інших журналів не експортувати.
4. Перемкнути CRM_PROJECTION_READ_MODE=bounded_range, повторити той самий ручний запуск. Кожен запуск — окреме виконання Apps Script. Не запускати обидва способи послідовно в одній функції: другий отримав би перевагу кешу.
5. Зібрати щонайменше 10 вимірювань кожного способу, чергуючи блоками A–B–B–A. Перші запуски після зміни коду позначати окремо. Використовувати однакові дані, паузи й умови, без паралельних вкладок/записів. Повторити на базах 3/100/250/1000 клієнтів; широкі аркуші перевіряти окремою серією.
6. Для кожної серії порівняти медіану, середнє та максимум sheets_verify.durationMs і repository_total.durationMs; окремо lock_wait. Відкидання невдалих операцій документувати, не змішувати їх з успішними. Перевірити відсутність stages.flush та failures=0. Не складати вкладені durationMs.
7. Додатково порівняти звичайні завантаження тестової CRM з тим самим чергуванням режимів. benchmarkCrmRead_ ізолює перевірку репозиторію, але не вимірює openById, підготовку bootstrap-відповіді чи мережу браузера; його repository_total не тотожний повному завантаженню CRM.
8. Після тесту видалити CRM_PROJECTION_READ_MODE і вимкнути CRM_DIAGNOSTICS_ENABLED. Для майбутніх досліджень передавати лише режим, розмір синтетичної бази та числові часи. Вибір стандарту для випуску вже завершено.

Контрольні вимірювання завершено власником; bounded_range обрано стандартом. Агент самостійно Google-вимірювань не виконував. Автоматичні перевірки підтверджують однакове виявлення пошкоджень і нуль записів тестового запуску, включно з відмовою при pending.
