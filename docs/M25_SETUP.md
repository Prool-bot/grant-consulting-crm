М2.5 — історична інструкція серверного етапу. Для повного інтерфейсу та публікації CRM 1.0 використовуйте [V1_DEPLOYMENT.md](V1_DEPLOYMENT.md), включно з файлом Index.html.

# Перше підключення Apps Script і Sheets — після окремого дозволу

Це підготовлена інструкція, а не команда виконати підключення зараз. М2.5 перевірено локально. Не використовувати старі таблиці, архіви заявок або реальні клієнтські дані. Вебзастосунок не публікувати на цьому етапі.

## 1. Перевірити код локально

У гілці `codex/m25-google-sheets`, Node.js 22+:

```sh
npm test
npm run build
git diff --check
```

Залежності не встановлюються. `dist/local` — незмінний браузерний М2; `dist/apps-script` — серверні `Server.gs`, `Code.gs`, маніфест і невикористовуваний локальний `Index.html`. `Server.gs` об’єднує домен, бізнес-логіку, адаптер і gateway у правильному порядку без `require`, npm або Node API. Функції генерації UUID й SHA-256 передаються з `Utilities`.

## 2. Перевірити потрібні OAuth-дозволи

У маніфесті лише:

| Scope | Навіщо |
|---|---|
| `https://www.googleapis.com/auth/spreadsheets` | Відкрити окрему CRM_DB через `SpreadsheetApp.openById`, створити її аркуші, читати й записувати рядки |
| `https://www.googleapis.com/auth/userinfo.email` | Додаткова серверна перевірка активної та ефективної ідентичності власника |

Повний Sheets scope потрібен для окремого файла за ID; `spreadsheets.currentonly` не підходить для такого способу відкриття. Дозвіл технічно ширший за один файл, тому код бере лише ID з приватної конфігурації, не приймає його від браузера й не шукає інших таблиць. Дозволи Gmail, Calendar, Drive API, зовнішніх HTTP-запитів і тригерів не потрібні. Факт локальної збірки не надає жодного OAuth-дозволу.

Офіційні джерела: [SpreadsheetApp.openById](https://developers.google.com/apps-script/reference/spreadsheet/spreadsheet-app#openById(String)), [Session](https://developers.google.com/apps-script/reference/base/session), [блокування і flush](https://developers.google.com/apps-script/reference/lock/lock).

## 3. Створити окремі приватні тестові ресурси

**Тільки після дозволу власника:**

1. Увійти в особистий Google-акаунт власника; перевірити профіль.
2. Створити **новий порожній** файл Google Sheets `CRM_DB_TEST`. Доступ — лише власник, без посилання для сторонніх. Не використовувати старі таблиці.
3. Створити окремий Apps Script-проєкт. Не додавати співредакторів: вони можуть бачити Script Properties і код, який має доступ до бази.
4. Зберегти ID таблиці й проєкту лише приватно. Не вставляти їх у цей документ, GitHub issues, PR, скриншоти або логи.

Сам адаптер створює структуру **всередині заданого файла**, а не файл Google Sheets чи проєкт Apps Script.

## 4. Завантажити збірку без додаткових залежностей

Рекомендований початковий шлях — ручний редактор Apps Script:

1. Створити файли `Server.gs` і `Code.gs`, скопіювати відповідний код із `dist/apps-script`. Не копіювати Node-тести чи локальні конфігурації.
2. У налаштуваннях проєкту ввімкнути показ `appsscript.json`; замінити його згенерованим маніфестом.
3. Перевірити `runtimeVersion: V8`, `timeZone: Europe/Kyiv`, два scopes і `webapp: {access: MYSELF, executeAs: USER_ACCESSING}`.
4. Зберегти. Не натискати публікацію/розгортання.

Альтернатива — `clasp`, якщо його встановлення й OAuth окремо погоджені. У цьому етапі його не встановлено. Перед використанням перевірити актуальні команди й ліцензію в [офіційному репозиторії clasp](https://github.com/google/clasp). `config/clasp.example.json` копіюється в ігнорований `.clasp.json`, ID заповнюється лише локально, корінь — `dist/apps-script`. `.clasprc.json` залишається поза Git і логами. Ручний шлях вище не потребує clasp.

## 5. Заповнити Script Properties

У Project Settings → Script Properties додати три властивості:

| Назва | Значення лише у приватному проєкті |
|---|---|
| `CRM_OWNER_EMAIL` | Власна адреса Google-акаунта |
| `CRM_SPREADSHEET_ID` | ID нової тестової таблиці |
| `CRM_ENABLED` | Спочатку `false`, після перевірки двох попередніх властивостей — `true` |

Шаблон `config/script-properties.example.json` має залишатися порожнім у репозиторії. Якщо потрібна локальна копія, зберігати лише як `config/script-properties.local.json` або в ігнорованій `private/`; не виводити її в термінал. Токенів чи ключів адаптер не потребує.

Порожня активна або ефективна адреса викликає відмову. Не обходити це вилученням перевірки: перевірити акаунт, авторизацію та режим виконання.

## 6. Ініціалізувати структуру

1. У редакторі власника обрати `setupCrm_` і запустити вручну. Під час першої авторизації перевірити два scopes, акаунт і приватність таблиці.
2. Перевірити появу шести аркушів сутностей і двох службових аркушів, описаних у [M25_SHEETS.md](M25_SHEETS.md). Початкова база порожня, без демоданих.
3. Повторити `setupCrm_`: не має бути нових аркушів чи повторних записів. Якщо заголовки несумісні, зупинитися; код не повинен очищати їх.
4. Повернення `{ok:false,...}` означає відмову. Не логувати дані для діагностики. Перевірити налаштування, заголовки, ліміти й наявність pending у приватному файлі.

Не підключати цю таблицю до іншого Apps Script-проєкту: блокування працює в межах одного проєкту. Не редагувати CRM-аркуші вручну й не вставляти формули.

## 7. Перевірити сервер на вигаданих даних

До дозволу на Google ці сценарії виконує `npm test` на імітації. Після дозволу — у приватному тестовому проєкті через ручну функцію перевірки, без журналювання вмісту:

1. `crmQuery({action:'listClients'})` повертає порожню сторінку та ревізію 0.
2. `crmMutate` з новим `Utilities.getUuid()`, ревізією 0 та `action:'saveClient'` створює вигадану організацію. Поля: `legal_name:'Демо: Тест'`, `type:'ngo'`, `status:'active'`.
3. Повторити **той самий** запит: той самий UUID клієнта, один запис і номер 0001. Не генерувати новий requestId при повторі.
4. Перечитати ревізію; змінити досьє із правильною версією. Повторити зміну зі старою версією та іншим requestId — має бути відмова.
5. Додати синтетичний контакт, взаємодію та заявку, перевірити зв’язки й `requested_amount`/`grant_id`.
6. Перевірити підтверджене м’яке видалення: видимість зникає, історія залишається.
7. Відновлення, обриви й квоти спочатку перевіряти локальними fault-injection тестами; навмисно пошкоджувати реальні файли не потрібно.

API, резервування та обмеження описані в [M25_SHEETS.md](M25_SHEETS.md). Немає автоматичного перенесення localStorage, імпорту чи читання архівів. Резервні копії не вставляти в код і не логувати.

## 8. Майбутня перевірка вебдоступу — окремий дозвіл

Режим **`MYSELF`** означає доступ тільки користувачу, який розгорнув застосунок; **`USER_ACCESSING`** — виконання під користувачем, що відкриває його. Це платформа Google, а не перевірка email у JavaScript. Див. [офіційний опис маніфесту](https://developers.google.com/apps-script/manifest/web-app-api-executable).

Маніфест не доводить, що старе чи вручну створене розгортання має ті самі права. Коли буде окремо погоджено публікацію та підключення інтерфейсу:

1. Вручну перевірити фактичні параметри нової версії: лише власник і виконання як користувач. Не використовувати `ANYONE`, `ANYONE_ANONYMOUS` чи `DOMAIN`.
2. Перевірити вхід власника, відмову іншому Google-акаунту та анонімному браузеру; перевірити серверні виклики, а не лише сторінку.
3. Перевірити, що приватні адміністративні функції недоступні через `google.script.run` ([документація](https://developers.google.com/apps-script/guides/html/communication#private_functions)).
4. Провести ручний огляд [SECURITY.md](SECURITY.md) та [ACCEPTANCE.md](ACCEPTANCE.md) перед реальними даними.

У М2.5 ці дії **не виконуються**. Налаштований `doGet` показує лише готовність сервера; повний браузерний М2 ще не працює через Google API.
