# CRM 1.2 — перше комплексне оновлення

Розроблено від `origin/main` (`3c158b6`, PR №7) в окремій гілці `codex/crm-1-2`. Назву гілки взято з прямого доручення власника. Реальні Google-ресурси, Script Properties, міграція робочої бази, merge та розгортання під час розробки не виконувалися.

## Реалізовано

- Нативні поля дати для дедлайну, подання, відповіді, наступної дії, взаємодії, документів і партнерських доказів. `YYYY-MM-DD` зберігається без часу. Реальні дні перевіряються, порожнє залишається невідомим. Старі ISO з поясом не мігруються; незмінне поле форми повертає точне початкове значення. Час старої взаємодії показується за Europe/Kyiv. Дедлайн «сьогодні» без часу залишається актуальним увесь київський день. Для змішаного сортування спочатку порівнюється київський календарний день, дата без часу перед часовими значеннями того дня; повні ISO впорядковуються за моментом, включно з повторною годиною восени.
- Головний реєстр: 5 колонок із групуванням, 6 без нього; посилання на клієнта в заголовку групи, `colspan=5`, сортування та доступність збережено. Порожній дедлайн не містить підпису часового поясу.
- Необов’язкове `applications.official_url`: HTTPS без облікових даних, безпечне відкриття; старі заявки не потребують URL. Поле зберігається в JSON заявки, а не створює окремий каталог конкурсів.
- ЄДРПОУ в каталозі клієнтів: чинне поле `edrpou_optional`, текст із провідними нулями, пошук і сортування; для фізосіб та відсутнього коду — «—».
- Документи: дев’ять категорій, назва, Drive-посилання, календарні дати, коментар, клієнт і необов’язкові заявка/партнерство; редагування та м’яке вилучення метаданих із підтвердженням. Файли не завантажуються, не читаються і не видаляються через CRM; права Google Drive не змінюються.
- Партнери: спільний довідник із типом, географією, сферою, контактами й примітками; багато-до-багатьох через `client_partners`. Наявного партнера можна приєднати до іншого клієнта. Однакова назва без урахування регістру й крайніх пробілів та повторний активний зв’язок блокуються. Є роль, статус, початок, коментар, меморандум і лист підтримки з датами та посиланнями на записи документів. Відв’язування не видаляє партнера, інші зв’язки або документи.
- Нові CRUD використовують білий список RPC, власника, ScriptLock, загальну ревізію, версію змінюваного запису й UUID запиту. Пов’язані записи перевіряються в тій самій транзакції; конкурентна зміна зв’язку спричиняє конфлікт ревізії. Історичні посилання на м’яко видалені записи зберігаються. Авторизований remote-кеш отримує також історичні записи для перевірки цілісності; інтерфейс їх приховує, у DOM вони не рендеряться.

## OAuth і приватність

Нових scopes і залежностей немає. Залишаються `spreadsheets` для бази та `userinfo.email` для додаткової перевірки власника. Drive, Calendar, Gmail і ШІ API не викликаються. Основна межа доступу — `MYSELF` / `USER_ACCESSING`; `CRM_ENABLED` і обидві ідентичності власника перевіряються також для приватних адміністративних функцій. Посилання на Drive не надає доступу до файла.

## Схема та зворотна сумісність

Зовнішній формат знімка `version:2` збережено. CRM 1.2 додає `modelVersion:12`, `documents`, `partners`, `client_partners` та службові метадані `migration12`. У `_crm_control` після початку підтвердження міграції встановлюється `schema:2`, щоб стара збірка не могла змінювати оновлену базу. Нова збірка читає стару схему для резервування/перевірки; завантаження нового UI просить ручну міграцію без автоматичної ініціалізації.

Нові аркуші мають ті самі колонки `id`, `client_id`, `version`, `data_json`. Міграція перевіряє старі проєкції проти підтвердженого журналу, ревізію й заголовки нових аркушів. Чужі непорожні аркуші не перезаписуються. Старий підтверджений знімок і контрольна сума залишаються в журналі; це **не заміна незалежної копії всього файла**. Усі старі записи, UUID, номери, версії, ISO та квитанції повторів зберігаються. Змінюється лише ревізія бази (+1) і метадані розширення.

Повтор міграції з тим самим початковим номером ревізії безпечний. Обрив до `pending` залишає старий підтверджений стан; порожні нові аркуші можна використати повторно. Обрив після `pending` завершується з журналу при наступному читанні/повторі. Не редагуйте аркуші вручну під час відновлення.

`restore` не дозволяє старому знімку стерти нові колекції; новий знімок також не можна завантажити у немігровану базу. Відновлення CRM 1.2 перевіряє всі зв’язки та збільшує версії відновлених записів, зберігаючи поточні квитанції й максимальний лічильник клієнтів.

## Ручний план власника: резервування → міграція → перевірка → випуск

Цей план підготовлено, але **не виконано**. Перед робочою базою повторіть його в окремій приватній тестовій базі на вигаданих даних. Один файл бази має обслуговуватися одним Apps Script-проєктом: ScriptLock не координує різні проєкти.

1. Погодьте вікно обслуговування. Закрийте всі вкладки CRM, дочекайтеся завершення/повтору непідтверджених записів. Збережіть чинну версію розгортання. Не запускайте `setupCrm_()` для оновлення або повторного засівання.
2. Після огляду коду перенесіть чотири зібрані файли CRM 1.2 у **наявний приватний Apps Script-проєкт**, не оновлюючи версію `/exec`. Це окрема ручна дія власника. Не запускайте deploy-workflow.
3. У редакторі з налагоджувачем викличте `inspectCrm12_()`. Результат має бути `ok:true`; занотуйте локально ревізію та кількості записів. Функція читає узгоджений стан і може завершити вже наявний `pending`, тому резервну копію робіть після успішної перевірки. Не друкуйте знімок, записи, URL або ID через Logger/console.
4. Тимчасово вимкніть доступ через `CRM_ENABLED=false`. У Google Sheets вручну виберіть **Файл → Створити копію** для всього CRM_DB, включно з усіма службовими аркушами. Збережіть її у приватному Drive власника під датованою назвою. Перевірте, що це незалежний файл, доступ лише власнику, усі аркуші/рядки й `_crm_control` скопійовані. Оригінал і копію не очищати. Не передавайте цю копію, її ID або скриншоти в Git/чат/логи. `backupCrm_()` повертає додатковий JSON-знімок, але не створює незалежного файла автоматично.
5. Для ручної міграції поверніть `CRM_ENABLED=true`; вкладки старої CRM залишаються закритими. Викличте **`migrateCrm12_(expectedRevision, true)`**, де `expectedRevision` — число з кроку 3, а `true` означає, що перевірену незалежну копію вже створено. Для запуску з меню редактора можна тимчасово додати приватну обгортку (суфікс `_`):

   ```javascript
   function runCrm12Migration_() {
     var expectedRevision = 0; // Замініть на перевірену ревізію; 0 — лише приклад.
     var result = migrateCrm12_(expectedRevision, true);
     if (!result.ok) throw new Error(result.message);
     debugger; // Перегляньте лише result у приватному налагоджувачі.
   }
   ```

   Не вставляйте резервний знімок у код. Обгортку не комітьте та приберіть після перевірки. Не запускайте функцію з `true` до кроку 4. Конфлікт ревізії означає: зупинитися, перевірити нові записи й створити свіжу копію; не підставляти нову ревізію навмання. У разі обриву повторіть той самий виклик із початковою ревізією. Якщо є помилка цілісності/чужі аркуші — зупиніться; не очищайте їх.
6. Повторіть `inspectCrm12_()`: `modelVersion=12`, ревізія на 1 більша, старі кількості ті самі, нові каталоги порожні. Перевірте `_crm_control.schema=2`, `pending=null`. Порівняйте UUID, номери, версії, `data_json` старих аркушів із приватною копією; зокрема записи, створені після CRM 1.1. Не експортуйте результат порівняння в публічні файли. Додатковий `backupCrm_()` має успішно повертати повний новий знімок лише у приватному середовищі.
7. У тестовій базі перевірте створення/редагування документів і партнерств, один партнер для двох клієнтів, м’яке видалення, повтори запитів і відновлення нового знімка через `restoreCrm_(snapshot, expectedRevision)`. Знімок передавайте лише з приватного сховища/пам’яті, не як літерал у коді. Перевірте старі дати, суми по валютах, контакти, архів і XSS. У робочій базі до випуску виконайте лише огляд наявних даних.
8. Проведіть ручний огляд `docs/SECURITY.md`, актуальні пункти `docs/ACCEPTANCE.md`, перевірку власника/стороннього акаунта та телефона. Лише після успіху оновіть наявне `/exec` на нову версію з `MYSELF` / `USER_ACCESSING`. Відкрийте CRM заново; старі форми не використовуйте.

### Відкат і відновлення

- До підтвердження міграції старий знімок лишається в журналі; за відсутності пошкоджень достатньо повтору того самого ручного кроку.
- Не знижуйте `schema` вручну та не запускайте CRM 1.1 проти мігрованого файла. Для повного відкату зупиніть доступ, збережіть ще одну незалежну копію поточного стану CRM 1.2 і всі записи після міграції. Перевіряйте стару резервну копію **окремо**, а не поверх нової бази. Перемикання приватного ID бази та старої версії розгортання — окреме ручне рішення власника після звірки нових записів.
- Для відновлення CRM 1.2 використовуйте знімок із усіма новими колекціями та очікуваною поточною ревізією. Спершу перевірте його на окремій приватній тестовій базі, де вже виконано міграцію. При втраті всього файла потрібна незалежна копія Drive; журнал у видаленому файлі не допоможе.

## Перевірки та межі готовності

Локальні перевірки: `npm test` (91 тест), `npm run build`, `node scripts/verify-cloud-release.js`, `git diff --check`. Нові автоматизовані тести охоплюють міграцію, нові транзакції й restore зі збоєм до/після кожного запису та flush; повторні UUID, конфлікти, зв’язки, старі знімки, небезпечні URL, дати/DST і ЄДРПОУ. Зібраний сервер тестується у VM без браузерного URL API, з імітацією Google та перевіркою відмови сторонньому користувачу.

`scripts/check-clients-ui.cjs`: Edge, 1440 і 360 px, 5/6 колонок, пошук ЄДРПОУ, date-picker, точне збереження старого ISO, нова дата без часу, офіційний URL, документи, партнерства/меморандум, XSS, підтвердження видалень, прокручування таблиць без переповнення сторінки. Використано вже наявний Playwright через `NODE_PATH`, нових пакетів не додано. Знімки лише із синтетичними даними збережено поза репозиторієм.

Обмеження: Drive-посилання перевіряється синтаксично, CRM не перевіряє існування файла або його фактичні права. Приймаються стандартні `/file/d/...` на drive.google.com та `/{document,spreadsheets,presentation,forms}/d/...` на docs.google.com; URL папок не приймаються. Прямого завантаження файлів і автоматичних резервних копій немає. Довідник партнерів доступний через вкладку клієнта; нечітке зіставлення назв не виконується. Дедуплікація однакових назв не замінює перевірку власником. Чинні ліміти повного знімка, комірок і журналу Sheets збережено.

**Код підготовлено до ручного приймання. Продуктивний випуск ще не підтверджено:** реальні Google OAuth/доступ, квоти, міграція робочої бази, незалежна резервна копія власника й приймання в Google не виконувалися.
