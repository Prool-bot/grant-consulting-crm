# CRM 1.3 — діагностика серверних етапів

Діагностика за замовчуванням вимкнена. Немає нових OAuth scopes, RPC-точок входу, залежностей чи змін моделі 12 / схеми Sheets 2. Журнал, контрольні суми, ревізії, requestId, flush і порядок відновлення не змінюються.

## Як увімкнути після окремого дозволу на тестове середовище

Власник використовує **окремий тестовий Apps Script-проєкт і тестову базу із синтетичними даними**. Лише в його Script Properties встановити обидва значення:

- `CRM_ENVIRONMENT` = `test`
- `CRM_DIAGNOSTICS_ENABLED` = `true`

Будь-яка інша комбінація, зокрема відсутні значення, вимикає діагностику. Параметри браузерного запиту не можуть її ввімкнути. Позначка test — явна конфігурація власника, а не автоматичне визначення походження бази: її не можна ставити на робочому проєкті. Цей PR не встановлює властивостей, не створює копій і не змінює розгортань.

Після тестів видалити `CRM_DIAGNOSTICS_ENABLED` або встановити `false`. Вимкнений режим не викликає годинник чи діагностичний вивід і не додає Sheets-операцій. Авторизація власника виконується до створення репозиторію: відхилений доступ не створює діагностичний звіт.

## Формат і трактування

Один JSON-рядок `console.log` після кожної операції під lock, також при помилці або таймауті отримання lock. Вивід відбувається після звільнення отриманого блокування. Збій виводу або годинника не змінює результат збереження та не приховує початкову помилку сховища.

Фіксований формат: `{kind:'crm_repository_timing',version:1,stages:{...}}`. Кожен етап має тільки числові `calls`, `durationMs`, `selfMs`, `failures`. Немає аргументів, результатів, текстів помилок, stack, назв клієнтів, UUID, email, Google ID, контрольних сум або вмісту знімків. Кількість ключів обмежена білим списком; звіт не накопичується між операціями та не записується у Sheets/журнал CRM.

| Етап | Що вимірює |
|---|---|
| `repository_total` | Отримання lock, операція та звільнення lock; без виводу звіту |
| `lock_wait` | `tryLock(10000)`, включно з очікуванням і відмовою |
| `control_read` | Читання й розбір керівної комірки |
| `journal_read` | Читання, складання, розбір і перевірка знімка журналу |
| `checksum` | Обчислення контрольної суми для перевірки/запису |
| `state_validate` | Валідація моделі й зв’язків знімка |
| `sheets_verify` | Нормалізація очікуваних проєкцій, читання всіх аркушів і порівняння заголовків/рядків |
| `journal_write` | Пошук місця, розширення за потреби й запис нових блоків журналу |
| `sheets_update` | Обчислення змінених проєкцій, запис аркушів і повне проєктування при recovery |
| `flush` | Кожен фактичний виклик `SpreadsheetApp.flush()` |

`durationMs` включає вкладені етапи; `selfMs` виключає їх. Наприклад, checksum/state_validate вкладені в journal_read, а flush після проєкції — у sheets_update. **Не додавати всі durationMs:** це подвоїть вкладений час. Для розподілу використовувати selfMs; repository_total.durationMs — загальний час. Відсутній етап означає, що він не викликався. Нуль мілісекунд можливий через роздільність Date.now. failures — число невдалих викликів без опису помилки; вкладена помилка також позначає батьківський етап невдалим.

SpreadsheetApp може відкладати застосування записів до flush, тому для оцінки вартості запису дивитися одночасно journal_write/sheets_update і flush. Час авторизації, openById, створення репозиторію, підготовки відповіді, мережі та холодного запуску **поза repository_total**. doGet не використовує SheetsRepository та не створює цього звіту.

## Вимірювання та наступна оптимізація

Надані власником реальні загальні часи: crmQuery 3,08–4,78 с; crmMutate 4,83–8,97 с; doGet 0,61–1,07 с. Це підтверджує залишкову серверну затримку після скорочення RPC, але не дозволяє приписати її конкретному етапу. Нових поетапних Google-вимірювань під час цього PR немає; робочі ресурси недоторкані.

На погодженому тестовому проєкті зібрати по 10 холодних/теплих читань і записів, окремо без конкуренції та з двома вкладками. В Apps Script Executions брати лише наш JSON-рядок, не експортувати повні журнали виконань чи параметри запитів. Порівняти медіану, максимум і частки selfMs, окремо успішні та невдалі операції. Повторити з діагностикою вимкненою, щоб оцінити її накладні витрати. Повтор requestId не слід змішувати зі звичайними записами: він має інший набір етапів.

Пропозиції за результатами цих вимірювань, у порядку встановленого домінування:

1. Якщо найбільший lock_wait — скоротити роботу всередині критичної секції, яку можна безпечно підготувати до lock; не переносити за lock перевірку ревізії/квитанції або підтвердження запису. Не скорочувати таймаут як заміну оптимізації.
2. Якщо sheets_verify / sheets_update — перевірити повторні звернення до об’єктів аркушів і кешувати **лише їхні handles на одну операцію**, а не значення чи результат перевірки; наступний кандидат — пакетний запис тільки змінених послідовних рядків після повної перевірки всіх проєкцій. Recovery залишити повним та ідемпотентним, додати тести кожної межі часткового запису.
3. Якщо control_read помітний — прибрати друге читання керівної комірки, передаючи під тим самим lock актуальний перевірений control, включно з новим покажчиком після pending recovery. Це потребує окремих тестів відновлення; зараз повторне читання збережено.
4. Якщо journal_read / state_validate / checksum — повторно використовувати вже нормалізовані структури тільки в межах операції, не пропускаючи читання контрольної суми нового журналу. Не вводити міжзапитний кеш перевіреної бази: він приховає сторонні правки Sheets.
5. Якщо flush домінує — спочатку оцінити кількість і розмір записуваних діапазонів. Поточні чотири бар’єри звичайного commit забезпечують порядок журнал → pending → проєкції → committed. Прибирати їх на підставі лише часу небезпечно; цей PR їх не змінює.
6. Якщо repository_total значно менший за загальний crmQuery/crmMutate — наступний замір має охопити відкриття Spreadsheet та підготовку відповіді, а не послаблювати перевірки репозиторію. Час doGet не є точним базовим значенням холодного старту інших викликів.

Це умовні пропозиції, а не твердження про вже встановлену причину затримки чи обіцяне прискорення. Спочатку отримати поетапні тестові заміри; вибрати оптимізацію за ними.

## Автоматичні перевірки

Тести перевіряють увімкнення лише через дві точні Script Properties, відсутність виводу в production та при відмові доступу, фіксовану схему без приватних маркерів, вкладені часи без подвійного підрахунку, невдале отримання lock, повторні читання, збої emit/clock та всі межі запису/flush із recovery й квитанціями. Наявні тести цілісності, приватного доступу, ревізій, дублювання й резервних копій збережено.

Звіт також містить фіксований projectionReadMode (data_range/bounded_range). [Контрольоване порівняння читання](V1_3_READ_COMPARISON.md).
